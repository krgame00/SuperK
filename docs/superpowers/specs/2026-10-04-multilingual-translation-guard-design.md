# Multilingual translation guard

## Approved intent

The user confirmed that contamination checking should follow every selected target language, across translation, quality review and saved work. The subsequent requirement is strict target-language output: Thai translations must contain no other-language lettering, including Latin names, SFX, brands and glossary entries. This supersedes the earlier permitted-Latin exception. Names are transliterated and SFX translated into the target writing system. Languages sharing a script require contextual review rather than a script-only assertion.

## Current constraints

The existing Unicode detector permits Thai/Latin and inherited marks. The image retry, page scan, saved editor and quality-review guard explicitly skip non-Thai targets. Quality review already receives the target language and source text. Keep bounded source-backed correction and explicit suggestion acceptance. Preserve saved text for repair; do not strip foreign letters or silently invent replacements.

## Approaches

1. Recommended: strict target-language script profiles, source-backed contextual review and a rendering/export gate. Local detection catches any excluded lettering without provider access; contextual review handles shared alphabets and transliteration. Unresolved output cannot be rendered/exported as translated text.
2. AI review alone: broader contextual reach, but no local protection when unavailable and greater dependence on model decisions.
3. Script profiles alone: fast and deterministic, but cannot distinguish English from French or Chinese text from Japanese kanji.

## Design

- Introduce a shared language policy module. Resolve exact normalized language names and locale aliases; do not infer language from arbitrary substrings. Support explicit script profiles for the application's targets and common international targets, including Latin, Cyrillic, Greek, Hebrew, Arabic, Thai, Han/kana, Hangul/Han and Indic scripts. Respect script-specific locales where a language has multiple writing systems. Japanese permits Han, hiragana and katakana; Korean permits Hangul and Han. Document the actual supported profile list rather than claiming all world languages have reliable identification.
- Check all Unicode letters/marks against the permitted target script set, including supplementary planes and scripts not named in the profile table. Thai permits Thai lettering only: Latin, Hebrew and every other script are rejected, whether standalone or embedded in a word. In Thai output, retain ASCII/Thai digits and ordinary punctuation/symbols; normalize other numeral forms to ASCII. Combining marks and joiners must be compatible with the target script and surrounding text; do not blanket-allow inherited linguistic marks. This covers contamination from any excluded Unicode script without maintaining a blacklist of possible source languages.
- Every target receives a contextual quality-review instruction: assess whether dialogue and suggested replacements are in the selected language. Transliterate names and brand terms, translate SFX and resolve glossary conflicts in favor of strict target-language output. For unknown/ambiguous targets, report that the target policy is unsupported and require a supported language/script choice before translated rendering/export. No silent fallback to Thai or permissive pass.
- Main workspace and extension expose the same target-language selector, defaulting to Thai and including explicit writing-system variants for languages with multiple scripts. Back-end validation must use the same canonical target identities.
- Use the same policy in source-backed correction, final page warning, whole-book scan, client/API quality-review guards, saved editor, every translated rendering path and export gate. Correct only affected point text from reliable source; preserve geometry, style and unaffected points. Missing source requires human repair. Allow one additional automatic correction batch per page/run, grouping affected point texts; validate the replacement once, then leave unresolved points for explicit retry/manual repair. The old full-image script retry must not add a second automatic correction on top of this budget; unrelated empty-detection recovery remains separate. Keep diagnostic text for editing, never display the rejected text on the translated image. Cover live canvas, cached assets, offscreen rendering, extension direct translation and publish-back.
- Same-script mismatches are handled by provider review. When contextual review is unavailable but local script validation passes, allow explicit human verification against the source to resolve the point. Detectable local script violations cannot be bypassed by provider approval, dismissal or manual acceptance. A contaminated provider suggestion is rejected locally; a clean suggestion still needs user acceptance. A provider review cannot guarantee perfect identification of short text in shared-script languages.
- Apply Thai-specific normalization only to Thai targets. Non-Thai output must retain native joiners, diacritics and formatting rather than pass through Thai cleanup.
- Preserve page data, original source, geometry and history. Existing pages are inspected locally on opening and before export; opening never initiates provider calls or silently rewrites stored text. Provide an explicit whole-book contamination repair command and preserve pre-repair text for undo. Store target identity with each saved page and verification metadata; editing text invalidates the relevant approval. Never use review approval from another target as proof of validity. On first opening a legacy project, require target confirmation with Thai suggested and persist it before verification. The next-job target selector does not reinterpret or rewrite existing page targets; saved pages retain target labels and require explicit retranslation to change language. This also applies to results saved in the reading extension.
- Clearly show affected points and the offending characters, with repair/retry controls. An unresolved point remains visible in the issue list/editor while its translated overlay is withheld. Block translated export with an actionable explanation rather than silently producing an incomplete page. The already-supported original-image export remains available by explicit page selection.
- Continue batch processing after an affected page. Before export, list affected pages and let the user repair them, explicitly choose original-image output for them or explicitly exclude them. Never silently omit pages, export incomplete translated overlays or change a page to original output without selection. Render/cache approval is tied to exact page text, target, background revision and policy version; stale live/cached pixels cannot bypass validation.

## Image-level source-text remnants

The user also requires inspection of original lettering left in cleaned backgrounds. This is a separate deliverable specified in `2026-10-04-source-text-remnant-review-design.md`. Its verification outcome and generated-text verification both feed translated-output eligibility. Complete both deliverables before claiming the full requested feature is ready.

## Coverage contract

Distinguish source contamination coverage from target-language coverage. For strict Thai, every Unicode letter/linguistic mark outside the permitted Thai profile is rejected, including scripts absent from the target-language catalog. Target language/script support is an explicit extensible catalog: Latin-script languages; Cyrillic-script languages; Greek, Hebrew, Arabic-derived languages; Thai, Lao, Khmer, Myanmar; Japanese, Chinese, Korean; Devanagari and other Indic writing systems; Armenian, Georgian and Ethiopic writing systems. Variant profiles identify the actual writing system rather than admitting all possible scripts of a language at once. The implementation plan must enumerate canonical target IDs, aliases and permitted scripts with data-driven tests. Unsupported/ambiguous entries are disabled with an explanation, never reported as verified. Shared-script linguistic judgments remain review decisions, not mathematical guarantees.

## Acceptance and verification

- Valid Thai, English, French, Japanese, Chinese, Korean, Russian, Greek, Hebrew, Arabic, Hindi and representative additional profiles are not flagged for their native scripts.
- Thai rejects every non-Thai letter, including permitted-Latin exceptions from the old implementation. Names, SFX and foreign-script glossary terms cannot bypass the guard. Cross-script contamination triggers bounded correction, warnings and suggestion rejection for other targets too. Deleted points remain excluded; legacy translated fields are checked.
- Locale aliases, multiple-script languages, unknown targets, supplementary characters, script-specific inherited marks, accented Latin, punctuation and numbers have regression fixtures.
- Shared-script wrong-language output is tested with mocked contextual review responses. Tests distinguish contextual approval from local script compatibility; no claim of perfect language detection. Unknown target policies, unavailable provider, failed correction and incomplete verification cannot silently pass rendering/export.
- Saved edits with stale/missing review metadata are checked against their saved page target, not the next-job selector. Explicitly changing a page's target through retranslation invalidates language-dependent review acceptance. Rejected output must not reach preview, canvas overlay, alternate rendering paths or translated export; original-image export remains an explicit choice. Dismissal/acceptance cannot bypass detectable script violations.
- Non-Thai normalization preserves Arabic joiners and decomposed marks. Existing Thai normalization behavior remains covered.
- Verify focused unit/hook/editor/API/export tests, TypeScript, changed-file lint and production build. Real provider calls using user work are excluded from automated verification. Service restart requires confirmation that current work is saved.
