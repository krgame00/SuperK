# CBZ Batch Translation Memory Design

## Problem and evidence

The user translated a 30–100 page ZIP/CBZ through the Windows browser-app shortcut. Chrome rose to about 6 GB, stayed there, and the app window closed. Task Manager showed 27.9/31.9 GB system RAM in use and heavy Chrome disk writes. Earlier Crashpad analysis in `docs/AI-WORKING-NOTES.md` identified a V8 out-of-memory crash during batch translation. Raising the V8 heap cap to 8 GB and shrinking the translated-image LRU did not prevent this recurrence. The new crash dump has not been read, so its exact exception remains unconfirmed.

The current code turns every imported CBZ page into a Base64 data URL and keeps those URLs in React state. `useTranslation` concatenates all page URLs with `pages.join("|")` on every render, including stopwatch updates. Autosave persists the full page URL list and uses `encodeURIComponent(pageUrl)` as an asset ID. Each completed page can therefore trigger repeated copying of large strings and metadata, while rendering also uses a full-size canvas and data URL.

## Decision

Use a stable short page ID for durable identity. Persist source pages as Blob assets and keep the session record compact. Preserve the existing runtime URL contract during migration, then move image access toward Blob-backed lazy URLs where all consumers can resolve them safely. Remove the per-render full-book string concatenation immediately. Keep the translated render cache bounded and release temporary canvas backing stores after export. Do not change Gemini routing, cleaning quality, page ordering, or export content.

## Data and compatibility

- New CBZ imports receive stable page IDs already generated by the workspace. Persist `source_<id>` Blob assets and compact page metadata that refers to those IDs.
- Legacy sessions containing data URLs must still load. On first successful save, migrate their source assets and compact metadata without losing bubbles or translated renders.
- Autosave must never replace a valid saved session with references to source assets that have not been committed. A failed source-asset write leaves the previous saved project usable and reports a save error.
- Bubble, clean-result, translated-image, and export lookup must resolve to the same page after reload, reorder, and cache eviction. User edits remain authoritative.
- Batch translation remains sequential by default. Its per-page temporary images are released after use; a previous completed page remains recoverable from persistent data.

## Acceptance

1. A synthetic 30–100 page CBZ-style project saves, reloads, and exports without storing image-sized keys or source data URLs in session metadata.
2. Progress rerenders do not concatenate every source URL or schedule unrelated autosaves.
3. Memory used by completed pages approaches a plateau instead of growing linearly through the batch; compare the same workload before and after, recording browser renderer memory at multiple page checkpoints.
4. Crash recovery restores all pages and committed translations. Existing project, cleaning, translation, and export tests pass.
5. The user's original CBZ is the final real-workload check if it is available. Until then, do not label the crash fixed.

## Delivery stages

1. Remove whole-book render-time string work and compact translated asset IDs, with red/green tests.
2. Persist source Blobs and compact project metadata with migration tests.
3. Replace remaining large runtime image representations where browser measurements show retention, preserving cleaning and export contracts.
4. Run the CBZ batch memory comparison and correctness gates; document measured results and limitations in `docs/AI-WORKING-NOTES.md`.
