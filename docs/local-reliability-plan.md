# แผนปรับปรุงความน่าเชื่อถือสำหรับการใช้งานบนเครื่อง

วันที่: 2026-09-05
สถานะ: แผนงาน — ยังไม่ได้ลงมือแก้ระบบ

## เป้าหมาย

ผู้ใช้ตรวจสอบได้ว่างานล่าสุดบันทึกสำเร็จหรือไม่ สามารถลองบันทึกใหม่เมื่อเกิดข้อผิดพลาด และงานคลีนที่ล้มเหลวไม่เก็บข้อมูลภาพที่ไม่จำเป็นค้างใน RAM

## ขอบเขต

- แจ้งสถานะการบันทึก session ลง IndexedDB และรองรับการลองใหม่
- คืนหน่วยความจำของข้อมูลภาพเมื่องานคลีนล้มเหลว
- พักประเด็น P1 เรื่อง Docker และสิทธิ์การใช้ API ตามการตัดสินใจของผู้ใช้ เนื่องจากขณะนี้ทดลองใช้งานเฉพาะบนเครื่อง
- ยังไม่เพิ่มการล้างประวัติ job ตามอายุ ต้องพิจารณาผลต่อการเปิดงานเก่าและ retry แยกต่างหาก

## ขั้นตอนดำเนินงาน

### 1. ส่งข้อผิดพลาดการบันทึกกลับถึงผู้เรียก

ไฟล์หลัก: `lib/projectStore.ts`, `hooks/useTranslation.ts`

- ตรวจเส้นทาง autosave และการเปลี่ยน session ก่อนแก้ไข
- ปรับ `saveProjectSession()` ให้ส่งข้อผิดพลาดกลับถึงผู้เรียก แทนการเขียน console warning เพียงอย่างเดียว
- แยกสถานะงานที่ยังไม่บันทึก กำลังบันทึก บันทึกแล้ว และบันทึกไม่สำเร็จ
- ผูกผลการบันทึกกับรุ่นของข้อมูล เพื่อไม่ให้ผลจากครั้งเก่าทับสถานะการแก้ไขล่าสุด
- รักษาการบันทึก session และ assets ใน transaction เดียวกัน

### 2. แสดงสถานะและรองรับการบันทึกซ้ำ

ไฟล์หลัก: `hooks/useTranslation.ts`, `src/app/page.tsx` และ component สถานะตามความเหมาะสม

- แสดงสถานะบันทึกใน workspace โดยไม่รบกวนการแก้ไข
- เมื่อผิดพลาด แสดงข้อความที่เข้าใจง่าย พร้อมปุ่ม “ลองบันทึกอีกครั้ง”
- เก็บการแก้ไขในหน่วยความจำไว้เมื่อบันทึกล้มเหลว
- การลองใหม่ต้องบันทึกข้อมูลล่าสุด และไม่สร้างคำขอซ้ำจากการกดหลายครั้ง
- เมื่อบันทึกสำเร็จ ให้อัปเดตสถานะเฉพาะข้อมูลรุ่นที่บันทึกสำเร็จแล้ว

### 3. คืนหน่วยความจำเมื่องานคลีนล้มเหลว

ไฟล์หลัก: `ocr-service/app/jobs.py`

- ตรวจเส้นทางงานปกติ งาน retry และเส้นทาง exception
- ล้าง `source_bytes` และข้อมูลภาพขนาดใหญ่ที่ job ไม่จำเป็นต้องถือครองหลังล้มเหลว
- เก็บ job ID สถานะ และข้อมูลข้อผิดพลาดไว้เพื่อให้หน้าจอตรวจสถานะได้
- ไม่ลบ assets หรือข้อมูลของ parent job ที่จำเป็นต่อ retry
- ไม่ถือว่าการคืน Python reference ต้องทำให้ค่า RAM ของ process ลดลงทันที เพราะ allocator อาจเก็บหน่วยความจำไว้ใช้ซ้ำ

### 4. ตรวจสอบผล

- เพิ่ม regression test จำลอง IndexedDB เขียนล้มเหลว: ผู้เรียกต้องรับรู้ข้อผิดพลาด และลองบันทึกใหม่สำเร็จได้
- ทดสอบการแก้ไขระหว่างบันทึก: ผลจากการบันทึกครั้งเก่าต้องไม่ทำให้งานล่าสุดแสดงว่าบันทึกแล้ว
- ทดสอบ UI สถานะผิดพลาดและปุ่มลองใหม่
- เพิ่ม regression test จำลอง cleaner ล้มเหลว: job ต้องไม่ถือข้อมูลภาพต้นฉบับ แต่ยังอ่านสถานะล้มเหลวได้
- ตรวจเส้นทาง retry ว่ายังใช้ parent assets ได้ตามเดิม
- รันชุดทดสอบที่เกี่ยวข้องและ TypeScript จากนั้นตรวจสถานะบนหน้าจอจริง
- อ่านคู่มือ Next.js ที่เกี่ยวข้องใน `node_modules/next/dist/docs/` ก่อนเขียนโค้ดตามข้อกำหนดของ repository

## เกณฑ์ตรวจรับ

- บันทึกล้มเหลวแล้วผู้ใช้เห็นสถานะผิดพลาด ไม่ถูกแสดงว่าบันทึกสำเร็จ
- ผู้ใช้ลองบันทึกใหม่ได้โดยไม่ต้องทำการแก้ไขซ้ำ
- สถานะบันทึกสะท้อนข้อมูลล่าสุด แม้มีการแก้ไขระหว่างบันทึก
- งานคลีนที่ล้มเหลวปล่อย reference ของข้อมูลภาพที่ไม่จำเป็น และยังแสดงสถานะงานได้
- การ retry และการเปิดผลของงานที่สำเร็จยังทำงานตามเดิม
- การทดสอบที่เกี่ยวข้องและ TypeScript ผ่าน

## ลำดับส่งมอบ

1. แก้เส้นทางบันทึกและสถานะ UI พร้อมทดสอบ เพื่อป้องกันผู้ใช้ไม่รู้ว่าข้อมูลยังไม่ได้บันทึก
2. แก้การคืนหน่วยความจำของงานคลีนที่ล้มเหลว พร้อมทดสอบ
3. ตรวจการใช้งานจริงและสรุปผลการตรวจรับ รวมข้อจำกัดที่ยังเหลือ
